## Issue Summary

Build a role template system that lets recruiters save, load, rename, and delete job role configurations (job title, seniority level, key skills) as reusable templates. Templates are persisted in a new `role_templates` SQLite table on the backend and managed through a dropdown on the `JobRoleForm` plus a management view for rename/delete operations.

---

## Problem Statement

Recruiters at hiring teams repeatedly fill the same job role configuration (e.g., "Senior Frontend Engineer" with skills like "TypeScript", "React", "System Design"). Currently, every new generation requires re-entering these fields manually. There is no way to save a role configuration for reuse, leading to repetitive data entry and inconsistency across generations.

---

## Current Behavior

1. Recruiter opens the HireIQ app.
2. Uploads a resume.
3. Fills in the `JobRoleForm`: job title, seniority level, key skills.
4. Clicks "Generate Questions".
5. If they need to generate for a similar role, they must re-enter everything manually.
6. No save/load/rename/delete functionality exists.

---

## Expected Behavior

1. **Save as Template:** After filling the `JobRoleForm`, the user can click "Save as Template" to give the current configuration a name and persist it.
2. **Template Storage:** Templates are stored in a new `role_templates` SQLite table with fields: `id`, `name`, `job_title`, `seniority_level`, `key_skills` (JSON array), `created_at`, `updated_at`.
3. **Load Template:** A dropdown on the `JobRoleForm` lists saved templates. Selecting one pre-fills all form fields.
4. **Manage Templates:** A management view (accessible from the main page) lists all templates with actions to rename or delete them.
5. **Rename:** User can rename a template from the management view.
6. **Delete:** User can delete a template from the management view, with confirmation.

---

## Root Cause Analysis

### Missing template domain

The current codebase has three domains: `health`, `resumes`, and `generate`. A new `templates` domain is needed to own the template persistence and CRUD operations.

### `JobRoleForm` has no persistence hook

The `JobRoleForm` component is purely stateless — it collects data and passes it to an `onSubmit` callback. It needs new state for the template dropdown, plus handlers for save/load operations.

### No template management UI

There is no existing view for managing any kind of saved data. A new template management view (or modal) is required.

**Request/Response Models (Pydantic):**

```python
from pydantic import BaseModel

class TemplateCreate(BaseModel):
    name: str
    job_title: str
    seniority_level: str
    key_skills: list[str]

class TemplateUpdate(BaseModel):
    name: str

class TemplateResponse(BaseModel):
    id: int
    name: str
    job_title: str
    seniority_level: str
    key_skills: list[str]
    created_at: datetime
    updated_at: datetime

    class Config:
        from_attributes = True
```

**Endpoint details:**

```python
from fastapi import APIRouter, Depends, HTTPException
from sqlalchemy.orm import Session
import json

from app.database import SessionLocal
from app.models.template import RoleTemplate

router = APIRouter(prefix="/templates", tags=["templates"])


def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()


@router.post("/", status_code=201, response_model=TemplateResponse)
def save_template(payload: TemplateCreate, db: Session = Depends(get_db)):
    """Save the current role form configuration as a named template."""
    existing = db.query(RoleTemplate).filter(RoleTemplate.name == payload.name).first()
    if existing:
        raise HTTPException(status_code=409, detail=f"Template '{payload.name}' already exists.")

    template = RoleTemplate(
        name=payload.name,
        job_title=payload.job_title,
        seniority_level=payload.seniority_level,
        key_skills=json.dumps(payload.key_skills),
    )
    db.add(template)
    db.commit()
    db.refresh(template)
    return template


@router.get("/", response_model=list[TemplateResponse])
def list_templates(db: Session = Depends(get_db)):
    """Return all saved templates, ordered by created_at descending."""
    return db.query(RoleTemplate).order_by(RoleTemplate.created_at.desc()).all()


@router.patch("/{template_id}", response_model=TemplateResponse)
def rename_template(template_id: int, payload: TemplateUpdate, db: Session = Depends(get_db)):
    """Rename an existing template."""
    template = db.query(RoleTemplate).filter(RoleTemplate.id == template_id).first()
    if not template:
        raise HTTPException(status_code=404, detail="Template not found.")

    existing = db.query(RoleTemplate).filter(
        RoleTemplate.name == payload.name,
        RoleTemplate.id != template_id
    ).first()
    if existing:
        raise HTTPException(status_code=409, detail=f"Template '{payload.name}' already exists.")

    template.name = payload.name
    db.commit()
    db.refresh(template)
    return template


@router.delete("/{template_id}")
def delete_template(template_id: int, db: Session = Depends(get_db)):
    """Delete a template. Returns 204 on success."""
    template = db.query(RoleTemplate).filter(RoleTemplate.id == template_id).first()
    if not template:
        raise HTTPException(status_code=404, detail="Template not found.")

    db.delete(template)
    db.commit()
    return None
```

**Error handling:**

- `409 Conflict` — template name already exists (on create or rename)
- `404 Not Found` — template ID does not exist (on rename/delete)
- `422 Validation Error` — required fields missing or empty (handled by Pydantic)

## Edge Cases & Risks

| Scenario | Mitigation |
|----------|-----------|
| Duplicate template name on save | Backend returns 409; frontend shows error message next to the name input |
| Duplicate template name on rename | Backend returns 409; frontend shows inline error in the rename input |
| User deletes a template that is currently loaded in the form | After delete, the form fields retain the old values (they are just state). The dropdown updates to reflect the new list. |
| User saves a template with the same name as an existing one | Backend returns 409 conflict. Frontend shows error and clears the name input. |
| Empty template name on save | Pydantic validation returns 422. Frontend shows error. |
| Very long template name (exceeds 255 chars) | SQLAlchemy `String(255)` will truncate. Add frontend validation to limit input to 255 characters. |
| Concurrent saves (race condition) | SQLite's default journaling mode handles concurrent writes gracefully. The 409 on duplicate name prevents overwrites. |
| Template with many skills (long JSON) | `Text` column in SQLite has no practical limit. No issue. |
| Management view open while form is being used | `TemplateManager` is rendered as a sibling section below the form. Both are visible simultaneously. |
| Network failure during save/load/rename/delete | `App.tsx` wraps all API calls in `try/catch` and displays error messages. No state mutation on failure. |
| User renames a template while the dropdown is open | The dropdown re-renders with the new name on the next fetch or via optimistic update. |

## Notes

- **No external dependencies:** The project uses inline styles throughout. All new components follow the same pattern — no new CSS frameworks or UI libraries required.
- **JSON storage:** `key_skills` is stored as a JSON string in SQLite. This avoids needing SQLAlchemy's `JSON` column type and keeps the schema simple. Parsing happens at the API layer (`json.dumps` on save, `json.loads` on read).
- **No template versioning:** At M3, templates are simple single-version records. If versioning is needed in a future milestone, add a `version` column and a separate `template_versions` table.
- **No template sharing:** Templates are local to the database. Multi-tenant sharing (per-recruper) is out of scope for M3 and would require an auth system (M2+).
- **No template import/export:** Export to JSON file or import from file is not required for M3. Can be added as a follow-up.
- **Dropdown ordering:** Templates are listed in `created_at DESC` order — most recently created templates appear first in the dropdown.
- **Management view placement:** The `TemplateManager` is rendered below the `JobRoleForm` in `App.tsx`, not as a modal. This keeps the implementation simple and consistent with the project's existing UI patterns.
