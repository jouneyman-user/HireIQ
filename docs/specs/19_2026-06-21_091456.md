## Issue Summary

Add a static **About Us** page to the HireIQ web app, populated with placeholder/mock content for now. The page should describe the company at a high level, list a few values, and provide a small team / contact block. It should be reachable from a top-of-page navigation bar that lets the user switch between the existing main view (resume upload + question generation) and the new About Us view.

This is **purely a frontend, mockup-level change** — no backend endpoints, no database changes, no authentication, no external services. The intent is to make the app feel like a real product with at least two navigable views, and to give designers / reviewers something concrete to iterate on.

## Problem Statement

The HireIQ app currently has exactly one screen (`App.tsx`) that does everything: resume upload, role form, question generation, and the resume list. There is no way to navigate to a marketing / informational page that describes what HireIQ is, who built it, or how to contact the team. New visitors landing on the app see only the tool, not the company behind it.

For a recruiting-focused product, the lack of an About Us page is conspicuous:
- Investors / reviewers expect at least one descriptive page.
- The team needs a place to park a mission statement, values, and contact info.
- A navigation bar is a prerequisite for adding future marketing pages (Features, Pricing, Contact, etc.).

This issue treats the About Us page as a **mockup**: copy is placeholder, layout is intentionally simple, and any production-grade content (legal text, real team photos, social links) is deferred until M3+.

## Root Cause Analysis

### Why a navigation bar is needed

`App.tsx` is a single, monolithic component. There is currently no abstraction for "which page am I on". Introducing the concept of a "page" — even just two of them — requires a tiny piece of state (`currentPage: 'home' | 'about'`) and a small render-time branch.

### Why state-based routing, not React Router

Options considered:

| Option | Pros | Cons |
|--------|------|------|
| **A** — State-based page switching in `App.tsx` (`useState<'home' \| 'about'>`) | Zero new dependencies; consistent with existing inline-style, single-file pattern; matches M1/M2 architecture ("solve for today's scale") | No browser URL support; no deep-linking; not scalable beyond ~3 pages |
| **B** — Add `react-router-dom` | Industry-standard, browser URLs, deep-linkable, scalable | New `dependencies` entry in `package.json`; learning curve; adds CWD-aware routing logic; over-engineered for a 2-page mockup |
| **C** — Render About Us as a section that is always visible below the existing screen | Simplest possible change | Not a "page" — defeats the issue's intent; can't navigate away from it; breaks UX expectations |

**Recommendation: Option A.** Per `CONSTITUTION.md` principle #2 (Standard Tooling Over Specialized Tooling) and #3 (Solve for Today's Scale), React Router is not justified for a 2-page mockup. State-based switching is consistent with the existing `useState` + conditional render pattern already used in `App.tsx` for `generateResult`, `generating`, etc. If real URLs / deep-linking / more than ~3 marketing pages become requirements, introduce React Router in a follow-up issue.

### Why a separate `AboutUs` component, not inline in `App.tsx`

Keeping `AboutUs` as its own component:
- Follows the existing one-component-per-file convention (`JobRoleForm`, `ResumeList`, `ResumeUpload` are all separate files).
- Makes unit testing straightforward (`AboutUs.test.tsx`).
- Keeps `App.tsx` small enough to reason about.
- Sets the pattern for future pages (`FeaturesPage`, `PricingPage`, etc.) to follow.

### Why no backend work

This issue is explicitly a mockup. All content is hardcoded inside the React component. There is no API call, no DB write, no auth, no routing. Backend remains untouched. This matches the issue description ("take it as a mockup page").

### Step 1 — `frontend/src/components/AppNavbar.tsx` (NEW)

Simple top nav bar with two buttons. Clicking a button calls `onNavigate('home' | 'about')`. Active link is styled differently (bold + underline).

```tsx
type Page = 'home' | 'about'

type Props = {
  currentPage: Page
  onNavigate: (page: Page) => void
}

const NAV_ITEMS: { id: Page; label: string }[] = [
  { id: 'home',  label: 'Home' },
  { id: 'about', label: 'About Us' },
]

export function AppNavbar({ currentPage, onNavigate }: Props) {
  return (
    <nav
      aria-label="Primary"
      style={{
        display: 'flex',
        gap: '1.25rem',
        padding: '0.75rem 0',
        marginBottom: '1rem',
        borderBottom: '1px solid #e2e8f0',
      }}
    >
      {NAV_ITEMS.map((item) => {
        const active = currentPage === item.id
        return (
          <button
            key={item.id}
            type="button"
            onClick={() => onNavigate(item.id)}
            aria-current={active ? 'page' : undefined}
            style={{
              background: 'none',
              border: 'none',
              padding: 0,
              cursor: 'pointer',
              font: 'inherit',
              color: active ? '#0f172a' : '#64748b',
              fontWeight: active ? 700 : 500,
              textDecoration: active ? 'underline' : 'none',
              textUnderlineOffset: 4,
            }}
          >
            {item.label}
          </button>
        )
      })}
    </nav>
  )
}
```
