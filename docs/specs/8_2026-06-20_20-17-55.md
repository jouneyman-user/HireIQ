# Issue Specification

> **Issue:** [#8 — Export interview sheet — download question set as formatted PDF](https://github.com/jouneyman-user/HireIQ/issues/8)
> **Date:** 2026-06-20
> **Effort:** S (Small)
> **Milestone:** M4 — Polish
> **Labels:** frontend, AI, feature

---

## Issue Summary

Recruiters need to export the AI-generated interview question set as a polished PDF document so that they can print it or share it with the hiring panel before the interview. The PDF must include the candidate name (when entered), the role title, the generation date, and all questions with their follow-ups and tips. Questions must be grouped by category under clear headings. The default download filename should be `role-title_date.pdf`.

This is a frontend-only polish feature. It does not require any backend changes, new database tables, or new dependencies.

---

## Problem Statement

After Milestone 2 (Issue #4 — `POST /api/generate` and Issue #5 — Question Display UI) recruiters can generate and view categorised questions in the browser. However, to actually run the interview they need a portable, printable artifact:

- There is no way to print or share the question set outside the browser session.
- Recruiters must currently copy individual questions to clipboard (manual, error-prone, doesn't preserve category structure).
- The hiring panel needs a single document that can be printed or attached to email — not a link to a web page.
- The PDF must look professional: title block, candidate name, role, date, clean category sections.

Without this feature, HireIQ's value stops at the screen.

---

## Current Behavior

1. Recruiter uploads resume + fills in the Job Role form.
2. Clicking "Generate Questions" populates the question display UI (collapsible Technical / Behavioural / Culture Fit sections with per-question copy buttons).
3. There is **no** mechanism to download, export, or print the question set.
4. The page itself would not print well — the upload form, role form, copy buttons, and toggle arrows are all part of the visible DOM.

---

## Expected Behavior

1. An **"Export PDF"** button appears next to the "Copy all questions" button at the top of the `<QuestionDisplay>` component.
2. Clicking the button opens the browser's native print dialog (user chooses "Save as PDF" as the destination).
3. The browser's default filename is `role-title_date.pdf` (Chrome/Safari use the document title as the default save name).
4. The printed/saved PDF contains, in order:
   - **Title block**: "Interview Questions" + the role title, candidate name (if entered), and generation date.
   - **Three category sections**: Technical, Behavioural, Culture Fit — each with a clear heading, the question count, and numbered questions.
   - **Each question** shows the main question text, the follow-up probe, and the "what to listen for" tip.
5. All UI chrome (upload form, role form, copy buttons, collapse toggles, sidebar, header navigation) is hidden in the printed output.
6. Page breaks are inserted between categories so each section starts on a fresh page (or near the top of the next page if the previous section barely overflows).

---

## Root Cause Analysis

### Why the issue is feasible in S effort

The existing `QuestionDisplay` component (from Issue #5) already renders the question set in a structured, semantic DOM — headings, sections, and question cards. The HTML is print-friendly by default; we just need a print stylesheet that hides chrome and a tiny handler that calls `window.print()`.

### Why no backend changes are required

The data is already in browser state (`generateResult` in `App.tsx`). The user has just generated the questions; sending them to the server to render a PDF would be wasteful round-tripping.

### Why no new dependency is required

Modern browsers ship with print-to-PDF capability. `window.print()` opens the dialog; the user picks "Save as PDF" as the destination. Adding `jsPDF` or `react-to-print` would increase bundle size for zero additional user-visible value.

### Filename control

Chrome and Edge use `document.title` as the default save filename when the user picks "Save as PDF". By temporarily setting `document.title = "Senior-Backend-Engineer_2026-06-20.pdf"` before calling `window.print()` and restoring it after the dialog closes, we get the desired default filename. Firefox uses a fixed `document.pdf` default — there is no standard cross-browser way to control the default, but the user can rename in the dialog. This is acceptable for an S effort.

## Proposed Solution

### Architecture

```
┌──────────────────────────────────────────────────────────────────┐
│                      PDF EXPORT FLOW                              │
└──────────────────────────────────────────────────────────────────┘

User clicks "Export PDF" button (in <QuestionDisplay />)
        │
        ▼
exportHandler(roleTitle, candidateName)
        │
        ├─ Set document.title = "<slug(roleTitle)>_<YYYY-MM-DD>.pdf"
        │  (Chrome/Edge use this as default save name)
        │
        ├─ Add class "is-printing" to <body> (CSS hook to hide chrome)
        │
        ├─ Call window.print() ────────►  Native print dialog
        │                                      │
        │                                      ├─ User picks destination
        │                                      │  ("Save as PDF" on most OSes)
        │                                      │
        │  ┌───────────────────────────────────┘
        │  │   (afterprint event fires)
        │  │
        ├─ Remove "is-printing" class from <body>
        ├─ Restore previous document.title
        │
        ▼
Cleanup complete; UI returns to normal
```

### What the print stylesheet does

The `@media print` block (in `src/index.css` or a new `src/print.css` imported globally) hides all interactive elements and reformats the document for paper:

- Hides: `.app-chrome` (upload form, role form, header navigation, copy buttons, collapse toggles, "Copy all" button, the export button itself).
- Shows: the document title block, all category sections (forced open), all question cards.
- Re-styles question cards: remove the absolute-positioned copy button, remove the colored follow-up/tip backgrounds (or convert to bordered blocks for ink savings), keep the bold question text.
- Inserts `page-break-before: always` on each `.category-section` except the first.
- Sets `@page` margins: 0.75in on all sides for US Letter / A4 compatibility.

### State flow

The `QuestionDisplay` component already receives the `questions` prop. We need to thread through two more pieces of metadata:

- `roleTitle` (string) — from the JobRoleForm submission.
- `candidateName` (string | null) — from the active resume (the `candidate_name` field on the `Resume` model).

`App.tsx` already has `activeResumeId` and the `resumes` list. It can derive `candidateName` from the active resume and `roleTitle` from the last submitted `JobRoleData`.

## Step 2 — `src/utils/slugify.ts` (new file)

A small helper to convert the role title into a safe filename fragment.

**Path:** `frontend/src/utils/slugify.ts`

```ts
/**
 * Convert a free-form role title into a filename-safe slug.
 *
 *   "Senior Backend Engineer"   → "Senior-Backend-Engineer"
 *   "iOS Engineer (Swift)"     → "iOS-Engineer-Swift"
 *   "  C++ / Systems Engineer " → "C-Systems-Engineer"
 *
 * - Replaces any run of non-alphanumeric characters with a single hyphen.
 * - Trims leading/trailing hyphens.
 * - Collapses to lowercase for cross-platform filesystem safety.
 * - Caps length at 60 chars to keep filenames under common 255-char limits.
 */
export function slugify(input: string): string {
  return input
    .normalize('NFKD')
    .replace(/[\u0300-\u036f]/g, '') // strip diacritics
    .replace(/[^a-zA-Z0-9]+/g, '-')
    .replace(/^-+|-+$/g, '')
    .toLowerCase()
    .slice(0, 60)
    .replace(/-+$/, '') // trim trailing hyphen introduced by slice
}

/**
 * Build the default export filename: "<role-slug>_<YYYY-MM-DD>.pdf"
 * Returns "interview-questions_<YYYY-MM-DD>.pdf" if the role is blank.
 */
export function buildExportFilename(roleTitle: string, date: Date = new Date()): string {
  const slug = slugify(roleTitle) || 'interview-questions'
  const yyyy = date.getFullYear()
  const mm = String(date.getMonth() + 1).padStart(2, '0')
  const dd = String(date.getDate()).padStart(2, '0')
  return `${slug}_${yyyy}-${mm}-${dd}.pdf`
}
```

## Step 3 — `src/utils/exportPdf.ts` (new file)

A small, self-contained export handler. Pure DOM manipulation, no React lifecycle entanglement.

**Path:** `frontend/src/utils/exportPdf.ts`

```ts
/**
 * Triggers the browser's native print dialog with the document
 * styled as a printable interview sheet.
 *
 * The default save-as-PDF filename is `role-title_date.pdf`
 * (Chrome and Edge use `document.title` as the default).
 *
 * Returns a cleanup function that the caller MUST invoke after the
 * dialog closes (e.g. on the `afterprint` event) to restore the
 * previous document title.
 */
export function exportToPdf(roleTitle: string, candidateName: string | null): () => void {
  const previousTitle = document.title

  // Build the suggested filename and temporarily set it.
  // Chrome/Edge will prefill this in the "Save as PDF" dialog.
  const filename = buildExportFilename(roleTitle)
  document.title = filename

  // Add a class to <body> so the print stylesheet can target
  // the document-header block (and any future print-only chrome).
  document.body.classList.add('is-printing')

  // Inject the document header (only visible during print).
  const header = document.createElement('div')
  header.className = 'print-header'
  header.innerHTML = `
    <h1 class="print-header__title">Interview Questions</h1>
    <p class="print-header__meta">
      <strong>Role:</strong> ${escapeHtml(roleTitle || 'Untitled')}
      ${candidateName
        ? `&nbsp;&nbsp;<strong>Candidate:</strong> ${escapeHtml(candidateName)}`
        : ''}
      &nbsp;&nbsp;<strong>Date:</strong> ${formatDate(new Date())}
    </p>
  `
  document.body.insertBefore(header, document.body.firstChild)

  // Cleanup: restore the previous document title and remove
  // the injected header + body class. Call this from `afterprint`.
  return () => {
    document.title = previousTitle
    document.body.classList.remove('is-printing')
    header.remove()
  }
}

/* ---------------- helpers ---------------- */

function escapeHtml(s: string): string {
  return s
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#039;')
}

function formatDate(d: Date): string {
  return d.toLocaleDateString(undefined, {
    year: 'numeric',
    month: 'long',
    day: 'numeric',
  })
}
```

## Edge Cases & Risks

| Scenario | Mitigation |
|----------|------------|
| User clicks Export PDF while generation is in flight | The `disabled` prop on the Export button (and the `exporting` state) prevents double-clicks; generation also disables the form |
| Browser doesn't support `window.print` (extremely rare in modern browsers) | `window.print` is a stable, universal API. No fallback needed; if absent, the click is a no-op. |
| User has only an A4 printer (not US Letter) | `@page { size: auto }` defers to the user's printer settings; we don't force a specific paper size |
| Role title is empty / whitespace-only | `slugify` returns empty string; `buildExportFilename` falls back to `interview-questions_<date>.pdf` |
| Role title has special characters (e.g. `</title>`) | `escapeHtml` in `exportPdf.ts` prevents XSS-style injection into the injected `.print-header` block |
| `afterprint` event never fires (very old browsers) | A 1-second `setTimeout` cleanup is registered as a belt-and-suspenders fallback. The title/class state is always restored. |
| Filename in Firefox | Firefox ignores `document.title` and defaults to `document.pdf` when saving. Acceptable for S effort; user can rename in the dialog. Documented in implementation notes. |
| User has a dark-mode browser theme | `@media print` explicitly forces `background: #ffffff; color: #000000` so the PDF is always light-on-dark text. |
| Page break splits a single question card across two pages | `page-break-inside: avoid` on `.question-card` keeps each card intact |
| Page break between question and its follow-up | Follow-up and tip are inside the same `.question-card` div, so they stay together |
| User wants to print just one category, not all | Out of scope for S effort; the entire question set is the artifact. Collapsed sections are forced open in print. |
| Long role title produces a very long filename | `slugify` caps at 60 chars; well under common 255-char filesystem limits |
| Filename collisions when exporting the same role twice in one day | Browser's print dialog appends `(1)`, `(2)`, etc. on collision. Acceptable. |
| User prints from the browser menu (Ctrl+P) instead of using the button | The print stylesheet is global, so the same polished output is produced. This is a free side-benefit. |
| Recruiter hasn't entered a candidate name | Acceptance criteria explicitly says "candidate name (if entered)" — the field is conditionally rendered; PDF is still produced with the role title and date. |

## Notes

- **Why no backend?** The question set is in browser state. Re-rendering it server-side is wasted round-trips. The acceptance criteria explicitly allows browser print-to-PDF.
- **Why not jsPDF / react-to-print?** Both add bundle weight for no user-visible benefit. `window.print()` already produces high-fidelity PDF output and is the simplest, smallest implementation. jsPDF would be the right choice if we needed a true `.pdf` blob download with no dialog, but that's outside the S effort.
- **Why not server-side reportlab?** Doubles the implementation footprint (new dep + new route + new layout code) for a polish feature. Reserving server-side PDF generation for cases where we need exact pixel-perfect, brand-controlled documents (e.g. invoices, contracts).
- **Cross-browser filename caveat:** Chrome/Edge honor `document.title` as the default save name. Firefox defaults to `document.pdf`. The user can rename in the dialog. This is documented but not "fixed" — there's no portable way to set a default save name across all browsers without using a server endpoint.
- **CSS hooks are deliberately generic:** `.app-chrome`, `.question-card__copy`, etc. are stable, low-coupling class names. They can be reused by future polish features (e.g. "Save as Markdown", "Email to panel").
- **Print stylesheet is loaded globally, not in the component:** This means users get the same polished output if they print via the browser menu (Ctrl+P / Cmd+P) instead of the button. The `.print-header` block is only injected when the button is clicked, but the rest of the print styling is always available.
- **Accessibility:** The export button has an `aria-label` ("Export questions as PDF"). The print header block uses semantic `<h1>` and `<p>` elements. No new keyboard traps.
- **Dark mode:** Forced to light theme in print, so PDFs are always readable when printed on paper (most printers still produce black ink on white paper).
- **Future enhancements (out of scope):** Save as Markdown (.md), Email to panel (mailto: with pre-filled body), Save as Word (.docx via server), Custom branding/logo in the header.
